# External validation: contribution and developer experience

Assessment conducted on 2026-10-08. The question was whether this repository
saves developers effort compared with tools and tests they already have.
Repository popularity is not evidence that it does.

## Applications inspected

| Application and pinned revision | Existing integration and testing | Validation performed |
| --- | --- | --- |
| [Chatbot UI Lite](https://github.com/mckaywrigley/chatbot-ui-lite/tree/3cb41ac08c3c9a234e703b3493fe3d8e243133dd) | Native fetch with a hardcoded OpenAI URL; stream ends on `[DONE]` | Original chat-handler and parser function bodies executed in a Node harness; full Next.js app not started |
| [Vercel Chatbot](https://github.com/vercel/chatbot/tree/c2f8235e1f3ea903ad8b7f61447c4f74164b5c58) | Test environment substitutes mock models through `lib/ai/providers.ts`; Playwright tests already exist | Source inspection only; app and SDK not executed |
| [LibreChat](https://github.com/LibreChat-AI/LibreChat/tree/e1dfc10449ff713faffacd60273fddcfe2c0a698) | OpenAI service tests mock dependencies; a mock Playwright workflow exists | Source inspection only; app and SDK not executed |

These are purposive examples, not a representative survey of all open-source
apps. Their tests show that endpoint interception is only one possible seam.
An integration must fit the project's existing tests before it deserves adoption.

## Reproducible execution

Run `npm run validate:external` on Node 24. The
[harness and source provenance](../validation/chatbot-ui-lite/README.md) are
checked in, including hashes and upstream licenses. All calls are local.

| Case | Observed result | What it establishes |
| --- | --- | --- |
| Direct fetch mock | HTTP `200 → 500 → 200`; healthy response content checked | Existing assertions can test the handler's simple provider-error behavior |
| Local proxy with actual handler | HTTP `200 → 500 → 200`; one injected request; two upstream requests | The proxy reproduces that behavior through sockets and reports disruption/recovery |
| Mock provider ends SSE without `[DONE]` | Handler output does not complete within the response-read deadline; healthy stream works after restoration | The runner detects incomplete output in this snapshot; truncation is generated by the mock provider, not by a new proxy feature |

The healthy stream contains one text event and a completion marker. This does
not test real SDK retries, tool calls, concurrent users, browser rendering, or
the app's deployed runtime. No application fix or upstream issue was submitted.

## Integration friction

The handler hardcodes its provider URL. The harness therefore needs a fetch
rewrite, a local provider, and an HTTP adapter around the edge handler. A normal
endpoint environment variable alone would not integrate it.

In this particular harness the direct-mock block occupies 19 nonempty,
noncomment lines; the proxy-comparison block occupies 34. This excludes shared
source loading, helper functions, cleanup, and the incomplete-stream case.
It is a description of this integration, not a general benchmark or a measure
of elapsed developer effort. More wiring yielded the same simple failure
assertion. The proxy adds socket behavior and a phase report, but this case
does not demonstrate that the developer needs those additions.

## Existing alternatives

[CopilotKit AIMock](https://github.com/CopilotKit/aimock/tree/999ee3915ee148040b880a8bbd9d9772e422fb8a)
already documents local provider mocks, Vitest/Jest helpers, failure controls,
request journals, and test identifiers. Inspection of
[its Vitest helper](https://github.com/CopilotKit/aimock/blob/999ee3915ee148040b880a8bbd9d9772e422fb8a/src/vitest.ts)
confirms server lifecycle hooks, environment setup/restoration, and fixture
count resets. Its
[journal implementation](https://github.com/CopilotKit/aimock/blob/999ee3915ee148040b880a8bbd9d9772e422fb8a/src/journal.ts)
maintains match counts by test identifier. Its
[chaos tests](https://github.com/CopilotKit/aimock/blob/999ee3915ee148040b880a8bbd9d9772e422fb8a/src/__tests__/chaos-latency-ratelimit.test.ts)
include latency and real-socket disconnect cases. This assessment inspected
source; it did not install AIMock or independently run its suite.

[JulienRabault/LLMock](https://github.com/JulienRabault/LLMock) also documents
Python pytest integration, SDK configuration, and provider failure scenarios.
That comparison is README-level only; its runtime was not exercised.

## Decision

Do not expand this standalone tool or recreate AIMock's test helpers now.
There is no demonstrated developer-experience advantage in the executed case.
Keep this repository as a small, reproducible experiment while evaluating a
specific gap in an existing application's tests.

The next useful contribution must reproduce a failure that existing tests
miss, use the application's normal test command, and verify a meaningful
application fix. Prefer adding that regression test to the application or
improving its existing mock tool. Only build additional infrastructure here
when that exercise demonstrates a missing capability. No viral-growth or
production-resilience claim follows from this validation.
